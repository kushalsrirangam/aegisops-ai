# Security boundary

The app has local password authentication and three roles. Operators can create incidents, run analysis, and ingest runbooks. Reviewers can approve or reject proposals. Admins can do both. All other incident and knowledge endpoints require a valid bearer session; the health and login endpoints are public. Approval identity comes from the authenticated account, not request content. Passwords use salted scrypt hashes, and opaque bearer sessions are stored as hashes, expire after 12 hours, and are revoked on logout. Create accounts with `python -m app.core.users_cli create-user --email you@example.com --role admin` after migrations.

Login throttling uses separate PostgreSQL buckets for a normalized account name and the request's client IP. Five failed account attempts or 30 failed IP attempts in a sliding 15-minute window cause a 15-minute cooldown. Successful authentication clears the account's failures but does not erase IP failures. Known and unknown account names receive the same 401/429 messages. The server uses the ASGI client address and does not trust an arbitrary `X-Forwarded-For` header. Behind a reverse proxy, configure trusted proxy forwarding before relying on per-client IP limits. A local operator with backend access can run `unlock-user --email <address>` or `reset-password --email <address>` through `app.core.users_cli`; a password reset revokes all sessions. Neither recovery operation is exposed through the API. The IP cooldown remains in force after account recovery.

This remains a local demo identity system. It lacks SSO, MFA, a supported account disable/rotation API, and stronger bot defense. Bearer tokens are held in browser session storage, so protect the frontend from script injection and use HTTPS for any shared deployment. Do not expose its write endpoints on the public internet yet. Agents produce analysis and proposals only. Approval records a decision; it does not run an action. Bedrock receives limited incident text and logs; never submit sensitive production logs without an approved data handling plan. Retrieved runbooks are displayed as cited data and cannot change graph instructions or allowed tools. The proposal policy is deny by default: only the cataloged migration review for the incident's service, with its exact review text, medium risk, and proposal-only mode, can reach approval. The trace records the policy reason. Production use needs action-specific authorization at the execution service. CloudWatch uses read-only API calls under an operator-supplied IAM role. Secrets belong in environment or a managed secret store, never Git.
